# Project bug audit and repair report

**Project:** Podhigai College website

**Date:** 11 October 2026 (Asia/Calcutta)

**Result:** Confirmed defects repaired locally; 54 automated checks pass. Staging acceptance remains necessary. This report does not certify that every possible defect has been discovered.

## 1. Scope and safeguards

Reviewed the public contact/admissions flows, shared JavaScript, mobile events, admin dashboard, Express API, startup/authentication/validation, static hosting, PM2 configuration, package dependencies, and the existing integration-test script. Checked local HTML links/assets and parsed public inline and external scripts. Backend and admin implementation were completed in two parallel workstreams and then reviewed and tested together.

The repository started with no tracked changes. No private `.env` or log content was read, no real MongoDB connection was opened, and no production API mutations, deployment, migration, commit or push were performed. The static-server smoke test used a temporary loopback listener and closed it. Tests use synthetic records and mocked persistence.

Frontend tests execute relevant code in Node VM contexts with DOM/network stubs. Only the static-hosting test performs actual local HTTP requests. There is no configured lint, typecheck or build script for this plain HTML/JavaScript project; none is reported as passed.

## 4. Open findings and limits — not a clean bill of health

1. **High, development dependency:** `braces` stack-exhaustion advisory [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) remains through nodemon/chokidar. npm proposes `npm audit fix --force` with a breaking downgrade to nodemon 1.14.10; that was deliberately not applied. Production-only installs exclude this chain. A separately verified watcher replacement or upstream patched release is needed to clear the full development audit.
2. **Authentication design:** Tokens retain the existing deterministic HMAC design without expiry or per-session server revocation. Removal of known defaults is not a complete session-management redesign. Rotate credentials/signing secret for deployment and consider expiring server sessions in a follow-up.
3. **Featured-event concurrency:** Saving the new featured event and demoting the others remains two MongoDB writes. Concurrent edits or failure during the second write are not transactionally atomic. A transaction/single authoritative featured reference and real database concurrency tests are still needed.
4. **Deployment integration:** Real MongoDB persistence, indexes, DB outages, reverse-proxy IP/rate-limit configuration, CORS from the actual hosting domain, websocket transport/reconnection and large uploads have not been tested in staging. Do not assume these are production-verified.
5. **Browser acceptance:** Mobile layout, keyboard/focus behavior, animations, assistive technology, image upload drag/drop and complete multi-tab/multi-device synchronization still need real-browser testing. VM tests are not visual end-to-end tests.
6. **Scale:** The dashboard fetches all message pages for client-side filtering. This fixes lost records, but a very large inbox needs server-side pagination/filtering and performance measurements. Public collection endpoints also remain unbounded.
7. **Legacy integration script:** It still changes chairman settings and creates contact/test records and does not fully clean up every failure path. It is gated, not made safe for shared data. Run it only against an explicitly disposable database. The burst scenario is not an assertion of UI debouncing.
8. **Previously browser-only enquiries:** Removing misleading local contact merging does not recover messages saved by older versions on visitors' devices. Recovery, if possible, needs a separate user-authorized process; no visitor data was inspected, deleted or migrated in this work.
9. **Content correctness:** Admissions years, fees, placement claims, institutional facts, example event schedules and the existing office-hours TODO require college approval. This audit did not independently verify factual marketing content.
10. **Migration utility:** `backend/migrate_to_atlas.js` was inspected but not run or certified. Backup-format/date conversion, collision handling and recovery need isolated migration fixtures before using it on real data.

## 5. Configuration and rollout checklist

### Required settings

Provide these through **backend/.env or deployment environment variables**, never in committed files:

- `MONGODB_URI`
- `ADMIN_USERNAME`
- `ADMIN_PASSWORD`
- `JWT_SECRET` — use a long random value
- `NODE_ENV=development` locally, or `production` when deployed
- `CORS_ORIGINS` — explicitly list the actual frontend origins in production, comma-separated
- Optional `SEED_DEFAULT_CONTENT=true` for deliberate initial sample-content setup only; unset afterward

See `backend/README.md` for full examples. Existing sessions must log in again. Production no longer implicitly allows localhost or arbitrary Firebase hosts. If using PM2 with its production backend setting and the local frontend, explicitly include `http://localhost:5500` and/or `http://127.0.0.1:5500` in CORS_ORIGINS.

The ignored `backend/.env.example` was updated locally by the backend workstream, but it is not a tracked deliverable. Required settings are also documented in tracked Markdown; no real `.env` was edited.

### Reproduce checks

From the repository root after installing dependencies:

```sh
npm test
npm audit --omit=dev
npm --prefix backend audit --omit=dev
```

To try the app against a configured development database, use separate terminals:

```sh
npm --prefix backend start
npm start
```

Open `http://localhost:5500`. The local frontend server binds only to loopback; external exposure requires an intentional hosting/reverse-proxy setup. No long-running preview server was left running by this audit.

### Staging acceptance before deployment

1. Start with a disposable staging database, explicitly configured credentials and exact frontend origins. Confirm backend startup and `db: connected` health.
2. Submit each enquiry form online and confirm the same enquiry appears on another device's admin dashboard. Simulate offline/timeout and verify no success claim and no lost form inputs.
3. Populate more than 100 synthetic messages. Check search, date filters, next/previous pages, mark-read, delete and authentication expiry.
4. Create/edit/publish/unpublish/delete events, including the last event. Restart with seeding disabled and confirm deleted content remains absent.
5. Upload/reorder/delete gallery items, save/reset chairman settings and verify fresh content on desktop/mobile and after websocket reconnection.
6. Test low-storage/quota failures, failed saves, HTML-shaped text and unusually large/invalid inputs.
7. Confirm the hosting service denies backend/config/log/report paths. Run production dependency audits in the deployment build.
8. Resolve or explicitly accept the remaining findings above before production rollout.
